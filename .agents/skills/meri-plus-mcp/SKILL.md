# Meri Plus MCP 校验闭环技能

## 技能目标

在修改 `meri-plus` 组件相关代码前，先用 MCP 完成组件能力核对，避免“猜参数/猜事件/猜样式类名”导致返工。

该技能默认用于：

- `meos-control-web` 工作区
- 涉及 `m-*` 组件（如 `m-table`、`m-pagination`、`m-popover`）
- 需要最小改动、快速验证、降低回归风险的场景

## 何时使用

当用户请求里出现以下意图时应优先使用：

- “给 m-table 加一个选中状态 / 高亮行 / active 行”
- “某个 m-* 组件参数怎么配”
- “我不确定这个组件是否支持某个 prop / slot / 事件”
- “先按组件文档来，不要拍脑袋改”

## 标准流程（必须按顺序）

### 1) 列出组件，确认目标组件名

先执行组件列表查询，确认组件真实名称（例如 `table` 对应 `m-table`）。

输出要求：

- 明确目标组件是否存在
- 若不存在，给出最接近的候选组件

### 2) 读取组件文档，确认公开 API

读取该组件文档，优先确认：

- props（名称、类型、默认值）
- emits / 事件
- 插槽与示例

输出要求：

- 只引用与当前需求相关的 API
- 标注“本次改动依赖哪些公开能力”

### 3) 读取组件源码，确认真实实现细节

读取组件源码，核对文档与实现是否一致，重点看：

- prop 在内部是否被消费
- 样式 class 的命名与触发条件
- 状态切换逻辑（如 active 行类名触发）

输出要求：

- 明确“使用该 API 会触发什么内部行为”

### 4) 读取组件样式，确认视觉表现与覆盖风险

读取组件样式，确认：

- active/disabled/hover 的 class 和颜色来源
- 是否需要业务侧额外覆盖样式

输出要求：

- 明确本次是否需要新增样式
- 若无需样式改动，明确说明“复用组件内置样式”

### 5) 在业务文件中做最小改动

仅修改与需求直接相关的代码，优先策略：

- 通过已有 props/computed/watch 对接组件能力
- 避免无关重构和大范围格式化
- 保持项目既有风格

### 6) 校验与收尾

至少完成：

- 目标文件错误检查（无新增报错）
- 说明改动点与回退逻辑（如有）
- 给出可复现的验证路径（点击/切换/数据变化）

## 决策分支

### A. 文档有能力，源码也支持

直接使用公开 API 接入，不引入自定义 hack。

### B. 文档有能力，但源码行为与预期不一致

以源码真实行为为准，业务侧做保守适配，并在结论中标注差异。

### C. 文档和源码都没有能力

不要硬塞未知参数；改为：

1. 给出可行替代方案（例如 `rowClassName` + 业务态）
2. 说明风险和影响范围

## 完成标准（质量门）

满足以下条件才算完成：

- 已执行完整 MCP 校验链路：
	- `list_components`
	- `get_component_doc`
	- `get_component_code`
	- `get_component_style`
- 业务改动是最小集，且每处改动都能映射到需求
- 目标文件无新增错误
- 结果说明包含：
	- 改了什么
	- 为什么这么改（对应组件能力）
	- 如何验证

## 推荐回复模板（给用户）

1. 先说明已完成组件能力核对（文档/源码/样式）
2. 再给出业务改动点（1~3 条）
3. 最后给出验证结果（错误检查、交互验证路径）
