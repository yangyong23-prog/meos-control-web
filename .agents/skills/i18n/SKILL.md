# meos-control-web i18n 使用技能

## 技能目标

在当前多应用工作区中处理国际化相关工作时，帮助代理稳定完成以下事项：

- 识别当前修改属于哪个前端应用，避免语言包改错位置。
- 复用已有 key，减少重复翻译与命名分叉。
- 为新增文案同时补齐中英文语言包。
- 在 Vue 模板、JS/TS、带插槽文本三种场景下，选择正确的 i18n 写法。
- 交付前检查占位符、命名空间、硬编码文本和多应用边界。

## 何时使用

当用户提出以下需求时，应优先使用本技能：

- “给页面加国际化 / 多语言”
- “把这段中文改成语言包 key”
- “补一下 zh.json / en.json”
- “这个文案要支持变量插值 / 富文本插槽”
- “排查 i18n key 缺失、命名不一致、英文没补全”
- “当前项目里 i18n 应该怎么写”

默认覆盖整个工作区内的 i18n 任务，但执行时必须先识别目标应用，再进入对应语言包与命名空间。

## 先判断目标应用

这个仓库是多应用工作区，国际化配置不是全仓统一一套，必须先确认目标应用：

### 根应用 `src/`

- i18n 入口：`src/localization.js`
- 语言包：`locales/langs/zh.json`、`locales/langs/en.json`
- 新增业务文案优先放在：`meos_control_web`
- 通用文案优先复用：`common`
- 带插槽文案组件：`src/components/I18nSlot.vue`
- 仓库中的常见写法：`i18n.global.t('meos_control_web.xxx')`

### 子应用 `operation-duty-homepage/`

- 使用子应用自己的 `src/localization` 和本地语言包
- 常见命名空间：`operation_duty_homepage`
- 不要把它的文案写进根应用 `locales/langs/*.json`

### 子应用 `meoi-aim-rcrm-web/`

- 使用子应用自己的 `src/localization.js` 和本地 `locales/`
- 常见命名空间：`rcrm_web`
- 不要误写到根应用语言包

### 总规则

1. 先看当前改动文件属于哪个应用目录。
2. 再看该应用自己的 `localization.js/ts` 与 `locales/`。
3. 不跨应用复用语言包，除非用户明确要求统一改造。

## 核心决策规则

### 1. 先复用，再新增

新增 key 之前先检查：

1. `common` 下是否已有语义一致的文案。
2. 当前业务命名空间下是否已有近义 key。
3. 附近文件是否已经在使用同一组 key。

只有在“语义不一致”或“当前业务需要独立命名”时才新增 key。

### 2. 命名空间选择

- 根应用新增业务文案：优先 `meos_control_web.xxx`
- 根应用通用文案：优先复用 `common.xxx`
- 子应用：优先使用该子应用已有命名空间，不混写到根应用命名空间

### 3. 按使用场景选择写法

#### 普通模板文案

默认优先跟随仓库现有风格：

```vue
{{ i18n.global.t('meos_control_web.xxx') }}
```

适用于大多数按钮、标题、标签、提示文本。

#### JS / TS / hooks / 常量文件

使用：

```ts
import i18n from '@/localization';

i18n.global.t('meos_control_web.xxx');
i18n.global.t('meos_control_web.xxx', { name });
```

适用于：

- `utils`
- `hooks`
- `constants`
- 配置项 label / title / message

#### 带插槽或富文本结构的文案

使用 `I18nSlot`：

```vue
<I18nSlot name-key="meos_control_web.exist_lighting_module">
	<template #count>
		<span>{{ count }}</span>
	</template>
</I18nSlot>
```

适用于：

- 文案中需要插入标签、强调色、链接、数字节点
- 不适合直接拼接 HTML 字符串的场景

### 4. 变量插值规则

- 优先保持中英文使用完全一致的占位符名称。
- 新增 key 时，优先使用具名参数：`{ name }`、`{ count }`、`{ val }`
- 如果周边已有明确的数组参数写法，并且同类 key 已经如此实现，可跟随现有模式
- 不要在中文与英文中使用不同参数名，否则运行时极易翻车

示例：

```ts
i18n.global.t('meos_control_web.name_success', { name });
```

对应语言包：

```json
{
	"meos_control_web": {
		"name_success": "{name}成功"
	}
}
```

```json
{
	"meos_control_web": {
		"name_success": "{name} succeeded"
	}
}
```

### 5. 避免错误做法

避免以下写法：

- 新增用户可见文案却保留硬编码中文
- 只改 `zh.json` 不改 `en.json`
- 在根应用页面里写子应用命名空间，或反过来
- 通过字符串拼接制造完整句子，导致英文语序无法调整
- 同一语义拆成多个碎片 key 再拼接
- 为了省事直接复制中文到英文而不标注风险

### 6. 超长国际化文本的样式兜底

生成界面代码或样式时，要默认考虑国际化后文本长度可能明显变长，尤其英文、德文、带变量插值或后台可配置文案场景。

如果用户没有明确指定展示策略，不要擅自只按中文长度写死宽度或高度；应主动提供以下两个可选方案，让用户自行选择：

1. **超出显示省略号**：适用于表格列、卡片标题、按钮、单行标签等空间固定区域。
2. **自动换行显示全文**：适用于说明文案、表单标签、详情区、弹窗正文等可接受增高的区域。

实现时至少满足以下要求：

- 说明当前代码采用的是“省略号”还是“自动换行”方案。
- 若尚未实现，仅给方案时，也要把两种选择明确告诉用户，而不是默认替用户拍板。
- 避免固定高度导致翻译后文本被裁切却没有任何可见反馈。
- 若组件所在区域同时存在中英文切换风险，优先检查是否需要 `min-width: 0`、弹性布局收缩、`word-break` / `overflow-wrap` 等配套规则。

常见实现参考：

- **单行省略**：优先使用项目内的 `v-ellipsis` 指令，并同时加上 `m-ellipsis` class，而不是只手写一组省略 CSS
- **自动换行**：`white-space: normal; word-break: break-word; overflow-wrap: anywhere;`

## 标准工作流

### 第 1 步：确认改动归属

1. 定位当前文件属于根应用还是某个子应用。
2. 找到该应用的 `localization.js/ts` 与语言包目录。
3. 明确应该操作哪一组语言文件。

### 第 2 步：搜索现有 key

1. 搜索现有业务命名空间下是否已有可复用 key。
2. 搜索 `common` 下是否已有通用表达。
3. 优先复用已有 key，避免一词多 key。

### 第 3 步：新增或更新语言包

1. 同时更新中文与英文。
2. 将新文案放到正确命名空间。
3. 保持中英文占位符一致。
4. 命名尽量语义化，不用无意义缩写。

### 第 4 步：替换代码中的文案使用方式

根据场景选用：

- 模板文本：`i18n.global.t(...)`
- JS/TS：`import i18n from '@/localization'`
- 插槽富文本：`I18nSlot`

### 第 5 步：完成后检查

交付前至少检查以下内容：

1. 所有新增用户可见文案都已国际化。
2. `zh.json` 与 `en.json` 都已同步更新。
3. key 路径与目标应用一致，没有跨应用误写。
4. 占位符数量和名称在中英文中完全一致。
5. 没有引入新的硬编码中文/英文。
6. 没有重复定义语义相同的 key。
7. 涉及界面展示的新增文案，已考虑超长国际化文本的展示策略，并在“省略号 / 自动换行”之间给出明确选择。

## 完成标准

满足以下条件才算完成：

- 修改点对应的语言包位置正确。
- 代码使用方式符合当前仓库习惯。
- 新 key 的中文、英文、占位符全部成对齐备。
- 页面上不再存在新增的硬编码用户文案。
- 若有富文本或插槽需求，使用了 `I18nSlot` 而不是危险拼接。

## 回答用户时的建议输出结构

处理完 i18n 任务后，建议按以下顺序反馈：

1. 目标应用与改动范围
2. 更新的语言包文件
3. 替换了哪些硬编码或补了哪些 key
4. 是否存在翻译语义仍需业务确认的项

## 本技能沉淀出的项目经验

1. 根应用当前实际语言包文件是 `locales/langs/zh.json` 与 `locales/langs/en.json`，以代码现状为准。
2. 根应用模板里常见写法是显式 `import i18n from '@/localization'` 后使用 `i18n.global.t(...)`。
3. `I18nSlot` 适合处理带节点插槽的文本，不适合再去拼 HTML 字符串。
4. 这个仓库是多应用结构，国际化改动前先分辨应用边界，比盲改更重要。
