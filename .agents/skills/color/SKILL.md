# meos-control-web 颜色使用技能

## 技能目标

在当前工作区处理颜色相关任务时，帮助代理稳定完成以下事项：

- 优先使用现有 CSS 变量，而不是直接写十六进制、`rgb()`、`rgba()`、`hsl()`。
- 先判断当前颜色是语义色、灰阶中性色，还是具体色板色，再选择最合适的变量。
- 保持与仓库现有写法一致，尤其是 `var(--token)` 与 `var(--token, #fallback)` 的使用习惯。
- 在样式块、内联样式、图表配置、组件 props 颜色字符串中，尽量统一使用 CSS 变量表达颜色。
- 只有在确认没有可复用变量时，才评估新增变量，而不是直接硬编码新色值。

默认策略是：**先不要新增全局颜色变量**。只有在明确存在复用价值、且用户希望沉淀为项目规则时，才评估补充新的全局 token。

## 何时使用

当用户提出以下需求时，应优先使用本技能：

- “这里的颜色不要写死，优先用 css 变量”
- “这个十六进制颜色在当前项目里应该替换成哪个变量”
- “当前项目颜色规范是什么”
- “主色 / 成功 / 危险 / 灰阶应该用哪个 token”
- “为什么这里要用 `var(--gray-600)` 而不是 `#626c78`”
- “图表 / 标签 / 内联 style 里的颜色怎么按项目规范写”
- “这个颜色值要不要抽成变量”

默认覆盖当前工作区里的颜色使用问题，但执行时必须先识别目标应用，再复用该应用已存在的颜色变量习惯。

## 先判断目标应用

这个仓库是多应用工作区，但在三个 Vue 应用里，颜色变量已经有明显共性。

### 根应用 `src/`

- 已大量使用 `var(--gray-600)`、`var(--blue-500)`、`var(--red-500)`、`var(--alpha-30)` 等颜色变量
- 常见写法同时包括：
  - `var(--token)`
  - `var(--token, #fallback)`
- 颜色经常出现在：
  - Vue SFC `<style>`
  - 内联 `style`
  - 组件 props（如标签、图表颜色）

### `operation-duty-homepage/`

- 同样大量使用 `var(--gray-800)`、`var(--orange-600)`、`var(--blue-500)` 等变量
- 常见写法也包括带 fallback 的：`var(--gray-600, #626c78)`
- 内联样式和业务配置对象中也会直接传入 `var(--...)`

### `meoi-aim-rcrm-web/`

- 同样以 `var(--gray-500)`、`var(--blue-500)`、`var(--red-500)` 等变量为主
- 在 SVG `fill/stroke`、边框、背景、文字颜色中都能看到变量使用
- 常见写法同样包括 fallback 版本

### `meos-daily-report-web`

- 当前不纳入这份技能的默认目标范围
- 它有自己独立的 React/CSS token 体系，如需约束，建议单独做专用颜色技能

## 当前仓库的颜色使用现实

### 1. 颜色变量已经是主流，不是例外

当前仓库能确认的大量现有写法包括：

- `var(--gray-600)`
- `var(--gray-600, #626c78)`
- `var(--blue-500)`
- `var(--red-500)`
- `var(--alpha-30)`
- `var(--primary-color)`（在颜色规范知识中也存在）

因此默认策略是：

- 新增颜色时，优先使用已有 CSS 变量
- 修改颜色时，优先把裸色值替换成已有变量
- 不要因为“写 hex 更快”就绕过变量体系

### 2. 语义色优先于色板色

如果颜色表达的是明确语义，优先选择语义变量，例如：

- 主操作 / 高亮：优先 `--primary-color`
- 成功态：优先 `--success-color`
- 危险 / 错误态：优先 `--danger-color`
- 警示态：优先 `--warning-color`
- 禁用态：优先 `--disable-*`

只有当场景不是语义色，而是明确的灰阶或色板层级时，再选择：

- `--gray-*`
- `--blue-*`
- `--red-*`
- `--orange-*`
- 其它 palette token

### 3. 中性色优先走灰阶变量

文本、边框、分割线、背景这类中性色场景，优先从灰阶里找：

- 文本：`--gray-900` / `--gray-800` / `--gray-600` / `--gray-500`
- 边框：`--gray-400` / `--gray-300`
- 浅背景：`--gray-100` / `--gray-50`
- 透明弱化层：`--alpha-30`

不要为了一个普通文本色去新造一套业务颜色变量。

## 变量选择顺序

默认按以下顺序选颜色：

1. **已有语义变量**
2. **已有灰阶 / 色板变量**
3. **现有文件附近已使用的 token**
4. **带 fallback 的已有 token 写法**
5. **确实没有可复用 token 时，再评估新增变量**

换句话说：

- 先复用
- 再贴近上下文
- 最后才新增

## `var(--token)` 与 `var(--token, #fallback)` 的规则

当前仓库两种写法都真实存在。

### 默认建议

- 如果当前文件或附近代码已经普遍使用 `var(--token, #fallback)`，优先保持一致
- 如果当前上下文已经稳定使用纯 `var(--token)`，可继续保持纯变量写法
- 不要无理由批量删除已有 fallback
- 也不要为了“保险”到处机械补 fallback，导致 diff 变脏

### 适合保留 fallback 的场景

- 附近代码已有同类写法
- token 命名历史上存在大小写 / 命名不完全统一现象
- 当前代码路径可能依赖外部主题注入
- 你无法 100% 确认该 token 在所有运行环境都稳定存在

## 在不同位置使用颜色的规则

### 1. 样式块中

优先：

```css
color: var(--gray-600);
background: var(--blue-500);
border-color: var(--gray-300);
```

不要默认写：

```css
color: #626c78;
background: #246fe5;
```

### 2. 内联样式中

如果必须写内联颜色，也优先用变量：

```vue
<div :style="{ color: 'var(--gray-500)' }" />
```

而不是直接塞 hex。

### 3. JS / TS 配置对象中

像图表配置、卡片配置、状态颜色映射等场景，也优先写：

```ts
color: 'var(--blue-600)'
```

而不是：

```ts
color: '#215dd9'
```

### 4. SVG / stroke / fill 中

同样优先：

- `fill: var(--blue-500)`
- `stroke: var(--gray-500)`

## 何时可以考虑新增颜色变量

只有在以下条件同时接近成立时，才评估新增变量：

- 当前场景找不到合适的已有语义色或色板变量
- 新颜色不是一次性临时色，而是有复用价值
- 新变量能放入合理的 token 层，而不是临时塞在某个局部文件里冒充全局规范
- 用户明确希望沉淀为项目规则

默认不要：

- 为单个组件的一次性颜色造全局 token
- 在业务组件局部随手写 `--my-red` / `--custom-blue`
- 一边已有 `--gray-600`，一边再造功能重复的变量

## 核心决策规则

### 1. 优先变量，不优先裸色值

只要当前仓库里已有合适 token，就优先变量。

### 2. 优先语义，不优先“最近的颜色值”

如果一个按钮是主操作按钮，优先 `--primary-color`，而不是因为某个 hex 更接近就改用 palette 色。

### 3. 优先跟随周边，不做局部“色彩革命”

修改现有文件时，先看附近已经在用哪些 token：

- 同类文本颜色
- 同类边框颜色
- 同类状态标签颜色
- 同类 hover / active / disabled 颜色

优先与周边保持一致，而不是自己重新发明一套映射。

### 4. 不为了“绝对纯粹”批量删 fallback

如果现有代码习惯是 `var(--token, #fallback)`，且运行环境存在不确定性，就保持它。别为了追求“最纯 token”把稳定性顺手砍了。

## 标准工作流

### 第 1 步：判断颜色语义

1. 这是主色、状态色，还是普通文本/边框/背景？
2. 如果有明确语义，先看语义变量。
3. 如果没有明确语义，再看灰阶或色板变量。

### 第 2 步：搜索附近现有 token

1. 先看当前文件附近同类元素在用什么颜色。
2. 再看当前应用里同类模块的颜色习惯。
3. 优先复用已有 token，而不是自己猜一个新值。

### 第 3 步：决定是否保留 fallback

1. 附近代码如果普遍保留 fallback，则跟随。
2. 如果上下文稳定用纯 token，可继续纯 token。
3. 不做无理由批量替换。

### 第 4 步：验证是否真的更一致

至少检查以下内容：

1. 是否把裸色值替换成了已有变量。
2. 是否选择了正确语义层级的 token。
3. 是否与周边文件颜色习惯一致。
4. 是否误造了重复 token。
5. 是否保留了必要的 fallback。

## 完成标准

满足以下条件才算完成：

- 新增或修改的颜色优先使用了已有 CSS 变量。
- 颜色变量的选择符合语义或灰阶/色板层级，而不是随意替换。
- 与周边代码的 token 使用方式一致。
- 没有无必要新增重复颜色 token。
- 若保留或新增 fallback，理由是清晰且合理的。

## 回答用户时的建议输出结构

处理颜色相关任务后，建议按以下顺序反馈：

1. 当前文件所属应用与颜色使用上下文
2. 选择了哪个 CSS 变量，以及为什么
3. 是否保留了 fallback 写法
4. 是否把裸色值替换掉了
5. 是否还有 token 缺失需单独沉淀

## 本技能沉淀出的项目经验

1. 根应用、`operation-duty-homepage`、`meoi-aim-rcrm-web` 三个 Vue 应用都已广泛使用 `var(--...)` 颜色变量，优先变量是符合仓库现实的，而不是新要求。
2. 仓库常见颜色 token 包括灰阶、蓝色、红色、橙色与透明层变量，例如 `--gray-*`、`--blue-*`、`--red-*`、`--orange-*`、`--alpha-30`。
3. 当前仓库同时存在 `var(--token)` 和 `var(--token, #fallback)` 两种写法；修改时应优先跟随周边习惯，不要批量做风格清洗。
4. 颜色变量不仅出现在 `<style>` 中，也出现在内联样式、组件 props、图表配置、SVG fill/stroke 等场景里。
5. `meos-daily-report-web` 有自己的 React 主题变量体系，不应把这份 Vue 颜色技能直接强套过去。
