## Context

当前末端系统已在 `ACOperationControl` 页面中实现了空间拓扑、壳配置消费等能力。本期需在此基础上接入新设备类：电动调节风阀、电动通断风阀、通风风机、风管式再热装置 ACATHT、空调机组控制组 ACAHG。改动涉及楼层地图、设备列表/详情、空间 hover/详情、半剖图、运行日志和图标。多数改动为新增配置和已有组件扩展，无需重构现有架构。

## Goals / Non-Goals

**Goals:**
- 实现新设备类的图形查询逻辑与配置表落表
- 楼层地图、全楼模型、设备列表、设备详情、空间 hover 和空间详情适配新设备类展示与交互
- 半剖图支持风口阀门参数展示、AHU 双盘/三盘扩展、新风机组部件扩展
- 新设备类运行日志接入与图标落地

**Non-Goals:**
- 不涉及壳配置的压差标准配置（独立 change）
- 不涉及 Dashboard 压差分布/模型统计/品质染色（独立 change）
- 不重构已有的设备详情或半剖图渲染容器

## Decisions

### 1. 新设备类查询依赖后端图形 DTO，前端不做聚合

决策：前端按 PRD 5.1 的图形边关系向后端请求设备范围，前端不自行拼装关系链路。

原因：电动调节风阀涉及 ACAirNetwork/VentNetwork 多层跳转，通风风机需取并集，前端聚合复杂度高且难以与后端一致。

### 2. 设备详情中的 ACAHG 复用聚合控制台模式

决策：空调机组控制组详情采用类似冷却塔控制单元的布局——聚合展示自身控制台 + 关联空调机组控制台 + 关联阀门控制台。

原因：PRD 要求在同一设备详情页展示多层对象控制，和冷却塔控制单元模式一致。

### 3. 半剖图部件扩展沿用现有部件编码体系

决策：新增 yure01/lengpanguan01/zairepanguan01 等部件，信息点存在性判断与原有规则一致。

原因：与现有半剖图渲染引擎兼容，只需追加配置与信息点映射表，不改渲染容器。

### 4. 运行日志复用现有日志框架

决策：新增设备类在现有日志框架中注册，设备范围逻辑由后端下发配置表中控制。

原因：PRD 5.4 注明"开发梳理末端管理设备范围"，前端只需按配置消费。

## Risks / Trade-offs

- [新设备类图形查询接口未就绪] → 接口联调前与后端确认 DTO 语义，前端先按 mock 数据开发
- [半剖图部件超过三个盘] → PRD 限定最多三个盘，超出部分作为未来扩展
- [ACAHG 两层嵌套详情交互复杂] → 复用现有冷却塔控制单元组件模式，不做自定义容器

## Migration Plan

1. 确认新设备类后端图形查询 DTO 与 6 张配置表
2. 楼层地图、全楼模型适配新设备类
3. 设备列表/详情新设备显示与控制
4. 空间 hover/详情压差与关联设备
5. 半剖图部件扩展
6. 图标 + 运行日志落地
7. 联调验证
