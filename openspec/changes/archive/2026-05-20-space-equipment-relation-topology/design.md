## Context

当前主应用的 `ACOperationControl` 已经形成了“左侧主内容区 + 右侧详情抽屉”的页面结构，并且页面内已有半剖图这类覆盖式视图能力。现有空间详情、设备列表、楼层地图和全楼模型可以展示对象结果，但缺少一条围绕“单空间设备关系”的统一链路页。

本次变更不是在现有 `CommonDrawer` 中新增一个 tab，而是在 `ACOperationControl` 页面内增加一个与右侧抽屉并列展示的独立拓扑区域。两者在 UX 上是并列关系，但实际宽度不固定为某个比例；`70% / 30%` 只是早期讨论示意，最终应允许按容器宽度和 UI 约束自适应。

同时，本次设计还需要把 AMC 壳范围配置真正消费到页面，包括空间设备关系入口模式、调度状态和控制目标值展示规则，并兼容“仅环境品质管理、无末端设备控制”的项目。实时环境参数本身不受壳配置勾选限制。

## Goals / Non-Goals

**Goals:**
- 在 `ACOperationControl` 中建立单空间拓扑页的宿主结构，使左侧拓扑和右侧详情抽屉可并列展示。
- 明确拓扑与抽屉的状态关系，支持从空间详情进入拓扑、在拓扑中点击设备覆盖右侧详情、关闭抽屉同步关闭拓扑。
- 明确前后端职责边界：后端返回空间、节点、关系等业务事实；前端负责 HTML + SVG 的节点排布和连线绘制。
- 明确壳范围配置在 dashboard、全楼模型、楼层地图、空间详情和拓扑入口中的统一消费方式，其中实时环境参数默认展示，控制目标值与调度状态按壳配置控制。
- 为无末端管理设备项目定义降级策略，确保页面隐藏无效控制入口但保留环境品质查看。

**Non-Goals:**
- 本次不复用现有 `RelationChart` 作为拓扑渲染容器。
- 本次不把拓扑页做成独立路由页，也不把它塞进 `CommonDrawer` 的 pane 体系。
- 本次不要求后端返回可直接绘制的 SVG 路径、坐标点或贝塞尔曲线数据。
- 本次不解决异常诊断、原因分析、影响链路推演等扩展能力。

## Decisions

### 1. 拓扑区域与详情抽屉采用“并列展示、依赖关闭”的关系

决策：左侧拓扑和右侧抽屉在 UX 上并列展示，但不是固定 70%/30% 比例。关闭左侧拓扑不影响右侧抽屉，关闭右侧抽屉会同步关闭左侧拓扑。

原因：
- 这符合当前讨论中“拓扑依赖抽屉存在”的交互预期。
- 可以避免把拓扑误建模成抽屉 tab 或独立页面切换。
- 与现有 `ACOperationControl` 宿主结构兼容，不必先重构 `CommonDrawer`。

备选方案：
- 把拓扑塞进 `CommonDrawer` 新 tab：被放弃，因为会把拓扑与详情混成单容器切换，无法支持拓扑常驻、抽屉切设备详情。
- 把拓扑做成全屏独立页面：被放弃，因为不符合当前“左侧拓扑、右侧详情”的联动需求。

### 2. 拓扑状态与抽屉状态解耦，拓扑只绑定空间上下文

决策：前端状态至少拆分为 `topologyVisible`、`topologySpace`、`topologySessionId` 三个核心状态；右侧仍使用 `showModuleInfo` 和 `currentSelectObj`。`topologySpace` 不随右侧详情对象变化。

补充约束：
- `topologyVisible` 的关闭触发器仅允许两类：用户手动关闭拓扑、用户关闭右侧详情抽屉。
- 在拓扑打开期间，从地图、设备列表、关联信息等非拓扑入口点击其他设备时，仅更新 `currentSelectObj`，不改变 `topologyVisible`，也不改变 `topologySpace`。

原因：
- 拓扑中点击设备后，右侧详情会切换为设备，但左侧拓扑仍然属于原空间。
- 如果直接复用 `currentSelectObj` 作为拓扑上下文，空间与设备详情切换会导致左侧拓扑上下文丢失。
- `topologySessionId` 可防止异步请求结果回写到旧会话。
- 显式收敛关闭触发器可以避免多入口点击设备时误触发拓扑关闭或空间上下文漂移。

备选方案：
- 只维护一个 `currentSelectObj` 统管左侧和右侧：被放弃，因为无法表达“左侧看空间、右侧看设备”的覆盖态。

### 3. 拓扑首版渲染采用 HTML + SVG，前端负责布局和画线

决策：节点区域采用 HTML 容器和业务卡片，边采用 SVG 绘制，首版按规则布局实现，不引入通用图引擎。

原因：
- 节点内容本身是业务卡片，HTML 更适合承载状态、指标和交互。
- 连线、箭头、高亮等更适合 SVG 实现。
- PRD 已明确存在“一个上游多个下游、多个上游一个下游”的关系，但现阶段仍更适合先走规则布局，而不是引入自动图布局复杂度。

备选方案：
- 复用 `RelationChart`：被放弃，因为其现有容器、配置场景和交互语义与本次单空间链路页不一致。
- 直接引入通用图引擎：暂不采用，首版复杂度过高。

### 4. 后端返回“关系事实 DTO”，前端不从列表或详情模板反推拓扑

决策：后端返回面向单空间拓扑页的业务 DTO，至少包含 `space`、`nodes`、`relations` 三层语义；前端根据这些事实完成分区、排序和连线绘制。

原因：
- 现有 `equipment-service-space` 等组件拿到的是“空间列表 + DETAIL 分组信息”，可作为查询参考，但不是拓扑关系结构。
- 如果前端继续从 `groupChildren` 或详情模板数据反推边关系，后续会因不同项目差异和链路配置扩展而不断返工。
- PRD 的核心不是“列出有哪些设备”，而是“把设备到空间的链路说清楚”。

DTO 草案：
- `space`：当前拓扑所属空间的摘要信息和环境参数。
- `nodes`：本图中的空间、空调设备、通风设备、控制组等可展示对象。
- `relations`：对象之间的连接关系事实，包含上下游方向和关系类型，但不包含 SVG 路径。

备选方案：
- 后端直接返回绘图坐标和线段：暂不采用，绘制方案由前端主导，且会增加后端与 UI 强耦合。

### 5. 壳范围配置消费统一收口到公共适配层

决策：空间设备关系入口模式、调度状态和控制目标值显示规则统一从壳配置读取层输出，不由各页面各自判断；实时环境参数保持按实例化规则正常展示，不受壳配置勾选限制。

原因：
- dashboard、全楼模型、楼层地图、空间详情和拓扑入口都要消费同一组规则。
- 分散实现会导致调度状态、控制目标值和入口显隐口径不一致，也容易误把实时参数错误隐藏。

备选方案：
- 每个页面单独消费壳配置：被放弃，因为会形成重复逻辑和行为不一致。

## Risks / Trade-offs

- [拓扑与抽屉的依赖关系复杂] → 通过拆分 `topologySpace` 与 `currentSelectObj`，并明确“关闭抽屉同步关闭拓扑、关闭拓扑不影响抽屉”的状态规则降低耦合混乱。
- [后端若只返回设备列表，不返回关系事实] → 在联调前冻结 `space + nodes + relations` 的返回语义，避免前端从详情模板或列表结果反推边。
- [规则布局可能不足以覆盖后续复杂项目] → 首版先用分区加规则排序落地；若后续项目证明需要自动布局，再单独评估图引擎或布局算法。
- [并列区域宽度不固定会增加响应式适配复杂度] → 设计上只冻结“并列展示”而不冻结固定比例，具体宽度交由宿主页按容器尺寸和 UI 约束计算。

## Migration Plan

1. 先补齐 change 对应 specs，冻结拓扑页和壳配置适配的需求边界。
2. 在前后端联调前先确认 DTO 语义、壳配置消费口径和无末端设备场景返回约定。
3. 前端先在 `ACOperationControl` 页建立并列宿主结构和状态收口，再接入拓扑数据请求与渲染。
4. 分阶段替换页面中的分散判断逻辑，统一切到壳配置适配层。
5. 如联调后需回滚，可先关闭拓扑入口消费和新宿主展示，仅保留现有空间详情与关联列表能力。
