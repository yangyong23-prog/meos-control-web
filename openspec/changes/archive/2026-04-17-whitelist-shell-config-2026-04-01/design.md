## Context

当前变更聚焦 ACOperationControl 壳配置中的“末端监测空间范围”能力，目标是在不改动多应用边界的前提下，统一默认推荐口径与白名单口径，并支持可追溯的增量维护。

约束：
- 仅改动主应用 `src/`，不影响 `meoi-aim-rcrm-web/`、`operation-duty-homepage/`、`meos-daily-report-web/`。
- 继续使用 Vue3 + Composition API + 既有 meri-plus 交互模式。
- 文本统一走国际化，空间编码与现有 IOT 规则编码保持兼容。

## Goals / Non-Goals

**Goals:**
- 建立末端监测空间范围配置模型，支持“引用全量可管控空间 / 用户配置白名单”两种模式。
- 提供白名单增量维护能力：按 IOT 维度追加、按楼层地图追加、去重、搜索、单条/批量移除。
- 保存后可稳定回显，确保下游页面读取同一口径。
- 保持前端筛选与空间状态计算性能可接受，不引入额外依赖。

**Non-Goals:**
- 不包含楼层地图入口配置功能本身的新增需求。
- 不包含照明/通风范围计算任务流程改造。
- 不在本变更中重构 ACOperationControl 全局状态架构。

## Decisions

1. 采用“模式 + 空间ID集合”的统一数据模型
- 方案：保存结构定义为 `mode`（`ALL_CONTROLLED` / `USER_WHITELIST`）+ `spaceIds`（白名单模式有效）+ `meta`（更新时间、操作者等）。
- 原因：便于后端幂等保存与前端稳定回显，也便于后续扩展黑名单或组合策略。
- 备选：仅存空间列表快照。未采用，因无法表达“默认推荐口径”语义，且回显歧义高。

2. 白名单采用“增量追加 + 统一去重（spaceId）”
- 方案：两个入口都先产出候选 `spaceIds`，再与当前白名单做并集去重；移除操作只影响白名单集合。
- 原因：符合 PRD 的“每次增量添加”语义，逻辑单一、易测试。
- 备选：按入口维护两份子集合再合并。未采用，状态复杂且批量移除语义不直观。

3. IOT 维度筛选使用“多选并集（OR）”
- 方案：用户勾选多个监测条件时，命中任一条件即纳入候选。
- 原因：与 PRD 文案一致，用户预期明确。
- 备选：交集（AND）。未采用，会显著缩小结果集并违背需求描述。

4. 列表展示采用“稳定排序”
- 方案：建筑按后端顺序、楼层按顺序号升序、空间按名称排序；搜索仅作用于当前白名单显示层。
- 原因：保证多次增量后展示可预测，降低核对成本。
- 备选：按加入时间排序。未采用，不利于跨楼层核对。

5. 前端状态组织遵循“本地编辑态 + 服务端持久态”
- 方案：进入页面拉取一次服务端配置作为基线，本地编辑态承载未保存变更；保存成功后覆盖基线，取消恢复到基线。
- 原因：可清晰定义“保存/取消”语义，避免模式切换污染。
- 备选：直接双向绑定服务端状态。未采用，交互回滚困难。

## Risks / Trade-offs

- [风险] 默认推荐口径与后端实现不一致导致回显差异 → [缓解] 联调阶段固化口径对照样本（建筑/楼层/空间级），并增加接口返回口径标识。
- [风险] 大项目空间量较大时，白名单搜索与批量选择卡顿 → [缓解] 搜索防抖、分页/虚拟列表预留；先保证去重与筛选纯函数可复用。
- [风险] 楼层地图与树选择双入口的选中态不一致 → [缓解] 统一落到 `selectedSpaceIds` 单一源，弹窗确认前仅操作临时态。
- [权衡] 先保持现有组件形态，减少跨模块改造范围 → 代价是后续若扩展更多策略需再抽象通用选择引擎。

## Migration Plan

- 发布策略：灰度发布至目标项目；若接口未就绪，前端入口保持禁用或降级提示。
- 数据兼容：后端无配置时，前端按默认模式展示，不阻断页面。
- 回滚方案：
  - 前端回滚到上一版本（不读新字段）
  - 后端保留历史配置数据，不做破坏性迁移
  - 若发现配置异常，可切回默认模式并重新保存覆盖。

## Open Questions

- 默认推荐口径是否需要在保存时固化为快照，还是始终按实时规则动态计算？
- 白名单上限（最大空间数）是否需要产品侧约束与提示？
- “按楼层地图追加”是否必须支持跨建筑批量勾选一次确认？
