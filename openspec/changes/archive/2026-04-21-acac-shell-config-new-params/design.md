## Context

本次变更来自 ACAC 壳配置 0402 迭代 PRD，目标是在主应用 `src/` 的壳配置页面中补齐空调冷源自动化需求计算条件输入缺失的参数。当前页面已经具备按分类渲染参数、保存配置、回显配置的基础能力，但尚未覆盖以下两类需求：

- 固定新增参数：加权平均温度差值 M，以及两处“供回水温差调整幅度配置”。
- 动态分组参数：通用工况下的“流量需求配置”，包含后端返回的设备实例范围选择和 3 个系数字段。

约束如下：

- 仅修改主应用 `src/`，不影响其它子应用。
- 新增文案必须接入国际化。
- 继续复用现有壳配置表单渲染和保存链路，避免为单次需求引入新的配置引擎。
- 对象范围和关系查询由后端在壳配置查询结果中直接返回，前端仅消费返回结果并处理交互约束，不扩展图模型。

## Goals / Non-Goals

**Goals:**

- 在 ACAC 壳配置中补齐 3 处固定新增参数，并落实默认值、必填性和输入范围约束。
- 为“流量需求配置”提供多组动态录入能力，支持设备实例选择、实例互斥、系数校验、保存回显。
- 保持前端职责收敛为渲染、编辑与保存，不额外承担对象关系查询或 BDTP 推送。
- 保持现有壳配置查询/保存页面结构与用户操作习惯不变。

**Non-Goals:**

- 不重构整个壳配置渲染框架。
- 不新增图关系维护能力，图关系查询仍依赖现有后端接口。
- 不在本次变更中扩展 ACAC 以外系统的壳配置参数。

## Decisions

1. 固定参数继续沿用现有壳配置基础字段模型
- 方案：将 3 个固定参数作为普通表单项接入现有分类渲染逻辑，沿用当前 number / range / 校验配置协议。
- 原因：这些参数没有动态结构，复用现有渲染链路成本最低，回显与保存也最稳定。
- 备选：为 ACAC 单独扩展一套局部表单实现。未采用，因为会制造额外维护面。

2. “流量需求配置”采用动态 rows 结构承载
- 方案：按“多组配置”建模为动态数组，每组包含对象实例集合与 3 个系数字段。
- 原因：与 PRD 的“支持添加多组配置”一致，也符合项目已有动态表单能力的表达方式。
- 备选：将每组配置拆成平铺字段。未采用，因为组数不固定，平铺字段会导致保存结构和 UI 都不可维护。

3. 已选设备实例在其它组内置灰，而不是直接隐藏
- 方案：同一实例已在其它组被选择时，在候选列表中保留但置灰，不允许重复选择。
- 原因：这与 PRD 描述一致，也能让用户理解为什么某些对象不可再选。
- 备选：直接从候选列表移除。未采用，因为会让用户难以判断对象是否存在还是已被占用。

4. 候选对象列表直接复用后端返回结果
- 方案：流量需求配置选择器直接消费壳配置查询结果中的候选项列表，不在前端追加 relationTo 查询、类型过滤或状态过滤。
- 原因：后端已经负责按图关系和状态筛选结果，前端继续补查会引入重复逻辑和联调偏差。
- 备选：前端基于 systemId 再次查询关系接口。未采用，因为这会和后端职责重叠。

## Risks / Trade-offs

- [风险] 动态 rows 保存结构与当前壳配置协议不一致 → 缓解：在设计阶段先固化字段结构和回显映射，避免实现时临时猜测。
- [风险] 后端若未返回完整候选项，前端无法自行补查对象范围 → 缓解：在 specs 中明确候选项由壳配置查询结果提供，联调时以接口返回为准。
- [权衡] 本次优先复用现有壳配置表单协议，代价是动态组配置会受限于现有渲染能力，而不是一次性抽象更通用的参数引擎。

## Migration Plan

- 先补齐 PRD 对应的 proposal、specs、tasks，再进入实现。
- 实现阶段新增参数渲染、动态配置结构与保存回显联动。
- 若上线后发现配置兼容问题，可回滚前端变更并忽略新增字段，旧配置页面不受影响。
