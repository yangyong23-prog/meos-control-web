# 信息点分精度影响范围梳理

## 一、背景

信息点分精度查询，目前分为两大类，一类是某些模块前端传**特定的请求头 IpType、startTime、endTime** 查询IOT数据，另一类是前端未传特定的分精度、开始结束时间的请求头查数据，以及后端未真正消费请求头查数据。

### 1、带特定请求头的数据查询

*   请求分精度相关数据：获取信息点数据的时间区间与 IP 策略类型，边端走 DTP 前缀，云端走 MEOS，目前都走的云端。`GET {isEdge ? INTERFACE_PREFIX_MEOS_DTP : INTERFACE_PREFIX_MEOS}/strategyIntervention/getInfoCodeDataTimeAndPrecisionType`
    
    ![image.png](https://alidocs.oss-cn-zhangjiakou.aliyuncs.com/res/meonar5PGrbpVqXx/img/949d328d-53e4-4369-a4ed-fd90d285c5a9.png)
    
*   其余接口查询逻辑现状：直接取已查到的分精度数据， startTime/endTime 直接取，**IpType 总是取返回的首个参数，即 ipTypes 数组里的第一个参数**。
    

![image.png](https://alidocs.oss-cn-zhangjiakou.aliyuncs.com/res/meonar5PGrbpVqXx/img/0727c335-48be-43de-b838-fe4ae5218f69.png)

### 2、不带/不消费请求头数据查询

第二类的话，分两种，一种是前端请求payload里传了分精度，比如运行监控看板这种，即使请求头有分精度，但仍以请求的payload里的分精度为准。

![image.png](https://alidocs.oss-cn-zhangjiakou.aliyuncs.com/res/meonar5PGrbpVqXx/img/b4b6db3e-161b-4835-8d4d-d069b5f649b2.png)

另一种主要是后台处理信息点数据查询的精度，前端暂无感知，比如老冷源查效率下的参数、SSE推数等。

## 二、影响模块及消费侧页面

通常来说，云端预先请求到分精度数据后，系统图header消费对应的开始时间，然后该模块下所有请求都会带上对应的分精度请求头（以下模块有相关接口的，都传了特定的请求头header），边缘端不带参。

## 三、相关接口改造方案

针对第一类带特定请求头数据的查询，制定相关接口改造方案。后端可以标记哪些接口真正涉及到分精度，前端再统一出改造接口的全量影响范围。

### 1、查项目壳配置，控制系统图 header 更新时间的显隐；

当壳配置的【“持久化数据查询逻辑”=查询距离当前最新的数据】时，系统图的页面和空间三维模型中均不再显示“更新时间”的内容

### 2、前端在指定要改的模块，要改的接口，加请求头特定标记；

原来请求头的传参不变，需额外加标记 **removeDefaultIpType = true**。

上面罗列的各个模块中涉及改动的接口：

*   冷源、冷热源、~~热源~~：涉及到分精度的【关系图/模型图、设备详情、设备列表、控制台】的接口
    
*   空调冷源、空调热源、空调冷热源：涉及到分精度的【关系图/模型图、设备详情、设备列表】的接口
    

### 3、改造时需评估影响范围，同步产品测试

冷源、冷热源、~~热源~~、空调冷源、空调热源、空调冷热源。**因为热源模块之前都没有请求头传参分精度，考虑到是老系统无大的变动，所以暂不更改热源模块。**

## 四、壳配置等

壳配置自定义配置，用户选择是否查询同一个时刻点的数据，若选择查询距离当前最新的数据，需设置距离当前的时间间隔，默认单位为1小时 1h，输入范围 1-168，即7天。
